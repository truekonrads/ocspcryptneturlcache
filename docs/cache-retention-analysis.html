Windows OCSP cache retention

An OCSP entry in Windows CryptnetUrlCache does not have one fixed lifetime. Protocol validity and physical file retention are controlled by different clocks.

  1. Validation lifetime: how long the response can satisfy a revocation check.
  2. Physical retention: how long its MetaData and Content files can remain recoverable.
if the response contains nextUpdate:
    valid_until = min(nextUpdate, certificate.NotAfter)
else:
    valid_until = min(thisUpdate + OcspValiditySeconds, certificate.NotAfter)

flush_base     = max(ExpireTime, LastSyncTime)
flush_eligible = flush_base + flush_exemption

The default OcspValiditySeconds is 43,200 seconds (12 hours). A stored dwExemptSeconds of zero selects the service default, normally 2,419,200 seconds (28 days). 0xFFFFFFFF disables automatic flushing for the entry.

Eligibility is not deletion. Reaching flush_eligible makes an entry eligible for removal during a later Cryptnet URL Cache Service scan. Expired files can remain recoverable beyond that time.

Response validity

cryptnet!OcspConvertResponseToCrl at 0x180009EC0 converts an accepted OCSP response into the time-valid-object representation used by Windows. It uses the response's nextUpdate when present. If the field is absent, it adds the value returned by I_GetOcspValiditySeconds at 0x18001CC38 to thisUpdate. In both cases it caps the result at the subject certificate's NotAfter time.

I_GetOcspValiditySeconds reads the OcspValiditySeconds DWORD under:

HKLM\Software\Microsoft\Cryptography\OID\EncodingType 0\
  CertDllCreateCertificateChainEngine\Config

An absent or invalid value produces the 12-hour default. HTTP Cache-Control: max-age, parsed elsewhere by cryptnet.dll, is response and revalidation metadata; it does not replace OCSP protocol validity.

On-disk fields that control retention

The current 116-byte metadata prefix contains the following retention fields. This is an observed implementation layout, not a documented file-format ABI.

OffsetFieldUse
0x10LastSyncTimeLast successful cache retrieval or update.
0x18Prefetch structure sizeValidates the prefetch block.

The flush block corresponds to Microsoft's CRYPTNET_URL_CACHE_FLUSH_INFO.

Normal eviction

The deletion decision is made in cryptsvc!EnumUrlCacheEntryCallback at 0x1800020A0. For a non-active-prefetch entry, the service:

  1. Uses the stored exemption, or the machine default when it is zero.
  2. Leaves the entry alone when the exemption is 0xFFFFFFFF.
  3. Chooses the later of ExpireTime and LastSyncTime, with clock-rollback handling for a future synchronization time.
  4. Adds the exemption and queues an eligible pair for deletion.

cryptsvc!InitPreFetchPara at 0x18000CD20 initializes the default exemption to 0x24EA00, or 28 days. A nonzero CryptnetDefaultFlushExemptSeconds DWORD under the chain-engine Config key can override it.

Queued entries are deleted by FlushUrlCacheEntries at 0x180008E04 during a service scan. The paired content and metadata files are separate; explicit deletion removes content first, so interruption or collection timing can leave an orphaned half-pair.

Active prefetch

An entry with a valid prefetch block, nonzero object type, zero prefetch error, and nonzero NextUpdateTime follows a different branch. The service creates or updates a prefetch job instead of placing the entry on the normal flush list.

Successful background refresh can advance LastSyncTime and replace validity metadata without the original application—or malware—running again. The normal formula is therefore not an upper bound for an actively prefetched entry. If prefetch is unsupported, malformed, or records an error, the entry falls back to normal time-based flushing.

Forensic interpretation

Presence establishes that certificate-related material was cached for that profile. It does not identify the initiating process, prove the inferred site was contacted, show that TLS succeeded, or establish that malware ran at LastSyncTime. OCSP retrieval may relate to a TLS certificate, intermediate CA, Authenticode signer, timestamp chain, or another validation operation.

Absence is also weak evidence. The entry may never have been created, may belong to another profile, may have been cleared manually, may have used stapled OCSP or another TLS stack, or may already have been scanned and deleted. Treat flush_eligible as a lower bound on automatic deletion, never as a guaranteed deletion timestamp.
